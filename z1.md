Занятие 1: Анализ предметной области и сбор требований
Цель: Научиться выявлять, классифицировать и формализовать требования.
Методики курса:
- Use Case Diagram (UML) – моделирование вариантов использования
- Спецификация требований (SRS - Software Requirements Specification)
- Матрица трассировки требований
Задачи для группы:
- Выделить акторов (Преподаватель, Студент, Администратор)
- Построить Use Case Diagram для каждого актора
- Классифицировать требования из ТЗ:
1. Функциональные (FR)
2. Нефункциональные (NFR)

Что такое требования?
Требования — это формализованные потребности stakeholders (заинтересованных сторон) к системе. Они делятся на:
1. Функциональные требования (FR) — описывают, что система должна делать
- Пример: "Система должна позволять преподавателю создавать тесты"
2. Нефункциональные требования (NFR) — описывают, как система должна работать
- Пример: "Время отклика не должно превышать 2 секунды"
- Категории NFR: производительность, безопасность, usability, надежность
Методика FURPS+ (для классификации NFR):
- Functionality — функциональность
- Usability — удобство использования
- Reliability — надежность
- Performance — производительность
- Supportability — поддерживаемость
+ другие (безопасность, scalability, legal)

Определение: Диаграмма вариантов использования показывает взаимодействие акторов (пользователей/внешних систем) с системой через use cases (варианты использования).

Ключевые элементы:
- Actor (Актор) — роль пользователя (Preподаватель, Студент, Администратор)
- Use Case (Вариант использования) — единица функциональности ("Создать тест", "Пройти тест")
- System Boundary — граница системы (прямоугольник)
- Associations — связи между акторами и use cases
- Include/Extend — отношения между use cases:
    - <<include>> — обязательное включение (базовый сценарий)
    - <<extend>> — опциональное расширение (альтернативный сценарий)

Правила построения:
- Use case должен представлять ценность для актора
- Название use case — глагол + существительное ("Создать вопрос")
- Один use case = один основной поток событий
- Избегайте технических деталей (не "Вызвать API endpoint", а "Сохранить ответы")
